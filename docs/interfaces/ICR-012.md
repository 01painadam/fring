# ICR-012: Inclination for the `core` distribution
Requested by: A4 (from K4), written by A0  Date: 2026-11-09
Status: Accepted (A0, 2026-11-09). AJ chose this option on 2026-11-09 ("ICR-012: `inclination` on core").

## What

1. **Config schema.** `[particles.distribution]` with `kind = "core"` gets an optional field `inclination_deg` (f64, degrees, default 0). It is the vertical epicycle amplitude i, the same for all particles (as `eccentricity` is): the height amplitude is `a i`.
   Rust: `Distribution::Core` in `crates/fring-model/src/config.rs` gets the field `inclination_deg: f64` with `#[serde(default)]`. Validation: finite and in [0, 90).
2. **Initial conditions.** In `crates/fring-model/src/physics/initial.rs`, the `Core` arm sets `EpicycleElements.i_rad = inclination_deg.to_radians()`. The vertical phase is `z_phase_rad = 2π u_z`. Here `u_z` is the second value of `rng.uniform_f64(counter(id, 1))`, which the core draw does not use now. So no new random numbers are drawn, and the draws of `a` and of the mean longitude do not change.
3. **Bit-identity at i = 0.** If `inclination_deg == 0`, the arm keeps `i_rad = 0.0` and `z_phase_rad = 0.0`, exactly as today. (With a random phase, `0 × sin φ` gives −0.0 for half of the particles, and that changes bit hashes.) So every existing config, golden hash and result stays the same.
4. **Not changed.** `band` and `eccentric_band` (they can get the same field later with another ICR), `epicycle_state`, the `Backend` trait, the snapshot format and the collision specification.

## Why

K4 compares the stochastic and the hard-sphere collision models (`docs/handoffs/K4.md`). Today every distribution starts at z = 0 and vz = 0 (`initial.rs`: "the distributions have no inclination field yet"). The K4 runs have no moons, so there is no vertical force at z = 0. Hard-sphere contact normals then stay in the plane, and the ring stays a flat monolayer for all time. The stochastic model gives random 3D impulses, so it becomes thick. Seed 1 at τ = 0.1, N = 10⁵, s = 10 m, 200 orbits, fit window orbits 80 to 200 (A4, branch `ws/a4-k4`):

| statistic | stochastic | hard sphere |
|---|---|---|
| c_ρ (mm/s) | 7.25 | 9.43 |
| c_φ (mm/s) | 3.63 | 5.14 |
| c_z (mm/s) | 4.73 | 0 (exact) |
| collisions per particle per orbit | 1.27 | 5.85 |
| ν (m² s⁻¹) | 0.0073 | 0.067 |

The two runs are different physical systems, so no agreement test is valid. A4 stopped the run queue after seed 1.

**Value for K4 (A0).** i = e / 2, the usual start for local ring simulations. At a = 140,220 km with e = 4 × 10⁻⁷: a e = 56.1 m and a i = 28.0 m (particle radius s = 10 m); i = 2 × 10⁻⁷ rad = 1.1459 × 10⁻⁵ deg. The rms vertical velocity at t = 0 is a i ν / √2 ≈ 2.3 mm/s, against the measured rms radial velocity 4.62 mm/s (pilot, t = 0). So c_z / c_ρ ≈ 0.5 at the start. The relaxed stochastic run gives 0.65, and the fit window starts after relaxation, so the exact start value does not matter much.

## Acceptance

1. All existing tests and golden hashes pass unchanged, in debug and in release (`cargo test -p fring-cpu --release --test golden`).
2. A new test: a `core` config without `inclination_deg` parses to 0 and gives the same states, bit for bit, as `inclination_deg = 0.0`.
3. A new test: with i > 0, for 10⁴ particles, max |z| ≤ a i (1 + 10⁻¹²), the mean of z / (a i) is near 0, and the rms of z / (a i) is 1/√2 within 3 standard errors. The in-plane state (x, y, vx, vy) is bit-identical to the state with i = 0.
4. Validation rejects a negative, non-finite or ≥ 90° `inclination_deg`.
5. The Definition of done, including the three wasm32 checks.
