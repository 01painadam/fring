## What

Everything below is opt-in. With the new config sections absent, `CpuBackend`, `GpuBackend`, `fring-run` and `fring-bench` keep their behaviour and their results, bit for bit.

### 1. Config (`fring-model/src/config.rs`, shared schema)

Two new optional tables in `RunConfig`, as `Option<...>` with `#[serde(default, skip_serializing_if = "Option::is_none")]`, like `diagnostics` (ICR-003). `deny_unknown_fields` stays.

```toml
[loss]                       # absent = today: a lost particle is an error
on_unbound  = "error"        # "error" (default) | "freeze"
moon_radius = "off"          # "off" (default) | "params"; "params" needs on_unbound = "freeze"

[substep]                    # absent = no sub-stepping
accuracy  = 0.1              # target value of h' v_eff / d_eff (the A2-ANALYSIS criterion); 0.07 to 1.0
max_level = 4                # n = 2^L sub-steps, L = 0 to max_level; at most 6 (n = 64)
```

- `moon_radius = "params"`: the radius of each moon in `[moons] include` comes from `radius_km` in `<params_dir>/moons.toml` (`moon_radii_from_toml_str`, matched by name, ICR-006 item 3).
- `[substep]` also reads these radii (the floor of `d_eff`, section 3). A missing radius is a `Config` error.
- `RunConfig::validate` returns `Error::Config` for: `moon_radius = "params"` with `on_unbound = "error"`; `[substep]` or `moon_radius` without moons; `accuracy` outside 0.07 to 1.0; `max_level > 6`; more than 4 moons with either key; and, in `GpuBackend` only, mode C with either key.
- Why `accuracy` has a lower limit: for a particle at any distance d from a moon, `v/d` is at most about the shear rate 1.5 n0, so `h v/d <= h x 1.5 n0 = 356.25 x 1.5 x 1.1756e-4 = 0.0628`. Below this value every particle would be sub-stepped everywhere. The check with `accuracy = 0.02` gave level 2 for all 22.7 million samples (`runs/logs/e1-icr-f.log`).
- No `trigger_hill` key. The rule of section 3 is the trigger (L > 0).

### 2. Lost particles: flag and freeze (all backends)

With `on_unbound = "freeze"`, `Backend::step` does not return an error for a lost particle. The particle is flagged and frozen. A particle is lost for one of these reasons (the numbers are those of ICR-006, status words included):

| Reason | Meaning |
|---|---|
| 0 | live |
| 1 | unbound or invalid orbit (the Kepler drift fails) |
| 2 + k | inside moon k (k = 0 to 5, moon order of the `System`): the minimum distance over a drift is less than `radius_km` |

Rules (the same on both backends):
- A frozen particle is not advanced, not binned for collisions, not counted in cell occupancy, not wrapped in the arc, and its chaos shadow is frozen with it. Cost: one load of its reason per block.
- **`drop_step`** is the 0-based global step (counted from the start of the run) in which the loss was found: the step whose Kepler drift failed, or whose drift segment hit the moon. It is exact and the same kind of number on the CPU and the GPU.
- **The frozen position is unspecified within one block.** The GPU keeps the state at the start of the block (ICR-006 item 2). The CPU does the same, with its own block length (4096 steps; the GPU uses `clamp(2e8 / N, 8, MAX_BLOCK_STEPS)`). So a consumer must use the reason and `drop_step`, not the frozen position, for physics. Tests do not compare frozen positions across backends.
- The `moon_radius = "params"` rule is the segment test of ICR-006: for each drift between two kicks (also the half drifts at the block ends), take the position relative to moon k at the two ends, interpolate linearly, find the minimum distance, drop if it is below `radius_km`. With sub-stepping on, every sub-drift is tested.
- With `on_unbound = "error"` nothing changes: `Error::Backend("particle <id> (index i) has an unbound or invalid orbit")`.
- In `GpuBackend`, `freeze` makes the existing word-0 check stop returning an error (it still sets word 0). The web (`GpuStepper`) is not changed by this item.

**Trait addition** (`fring-model/src/backend.rs`), a provided method like `chaos()` in ICR-003, so existing implementors still compile:

```rust
pub const DROP_LIVE: u8 = 0;
pub const DROP_UNBOUND: u8 = 1;
pub const fn drop_inside_moon(k: usize) -> u8 { 2 + k as u8 }

#[derive(Clone, Debug, Default, PartialEq)]
pub struct DropReport {
    pub time_s: f64,                // simulation time of the report
    pub reason: Vec<u8>,            // per particle, in ParticleView order; 0 live
    pub drop_step: Vec<u64>,        // per particle; u64::MAX only for a live particle
    pub n_unbound: u64,             // cumulative since the start of the run
    pub n_inside_moon: Vec<u64>,    // cumulative, per moon, in System order
}

fn dropped(&mut self) -> Result<Option<DropReport>> { Ok(None) }
```

`dropped()` returns `None` when the config has no `[loss]` with `freeze`. A GPU backend reads its status buffer back here, so do not call it every step. `StepStats` and `ChaosReport` get **no new field** (see Migration): `ChaosReport.flags` bit 1 (value 2) means "dropped" (bit 0 is unchanged).

**Output (AJ decision 4):** `fring-run` writes `drops.csv` to the run directory at the end of the run (and also when the run stops with an error), with the header `id,reason,drop_step,time_s,x_km,y_km,z_km,vx_km_s,vy_km_s,vz_km_s`: one row per lost particle, ordered by id, the frozen inertial state (unspecified within a block), `time_s` = `start + drop_step x step_s`. The frame format and `stats.csv` do not change. Frames still contain frozen particles at their frozen position: a reader that needs the live set joins `drops.csv` (live at frame step s means `drop_step >= s` or not in the file). The section "8b. `drops.csv`" goes into `docs/snapshot-format.md` (additive to version 1, like 8a).

**GPU status buffer** (A3 confirms in E1-GPU): it grows from `8 + cap` to `8 + 2 cap` `u32` words. Words 0 to `8 + cap - 1` keep the ICR-006 meaning. Word `8 + cap + i` = `drop_step` of particle i (low 32 bits; `u32::MAX` = live). The kernel needs the global index of the first step of its block in the `prm` words. 2^32 steps is 1.5 million years at h = 356 s, so 32 bits are enough. `bin.rs` only checks `status.size() >= 4 (8 + cap)`, so it still works.

### 3. Sub-stepping: the rule (both backends)

Block time steps with synchronisation at every global step: all particles are at the same time at every multiple of h. Collisions, the arc wrap, outputs and the chaos renormalisation therefore see an ordinary particle. Step k runs from `t_k = start + k h` to `t_{k+1}`; its kick is at `t_k + h/2`.

**What a level means.** Step k is done as n_k = 2^L_k Wisdom-Holman steps of h/n_k. The sub-kicks are at `t_k + (j + 1/2) h/n_k` for j = 0 to n_k - 1. In the merged-drift form (`wh_steps_moons`), the drift between the last kick of step k-1 and the first kick of step k is `h/(2 n_{k-1}) + h/(2 n_k)`. This is exact, because Kepler drifts compose. With L_k = 0 the operations are those of today's loop, bit for bit.

**Which state chooses L_{k+1}.** The last kick of step k (at time `t_c`, where `t_c = t_k + h/2` if L_k = 0, and `t_c = t_{k+1} - h/(2 n_k)` in general). At that kick the particle position `p` is known and unchanged by the kick; the velocity `w` is the velocity after the kick. The kick already computes `|p - m_j|`, so the extra cost is small. For each moon j:

```
d      = |p - m_j(t_c)|                 u = |w - mdot_j(t_c)|           (km, km/s)
dt     = t_{k+2} - t_c = h + h/(2 n_k)  (the time to the end of step k+1; 1.5 h if L_k = 0)
d_eff  = max(d - u dt, r_j)             (r_j: radius_km of moon j; this is the margin and the floor)
v_eff² = u² + 2 GM_j / d_eff            (gravitational focusing)
L_j    = smallest L in 0..=max_level with  h v_eff / (2^L d_eff) <= accuracy ; max_level if none
L_{k+1} = max over moons of L_j
```

- Each particle keeps one `u8` "next level" between steps and between `Backend::step` calls (CPU: a `Vec<u8>`; GPU: a buffer of `cap` words, A3 decides where). Value 255 = unknown. The state at a block start therefore does not matter for the rule. This is the answer to the block-start question: the decision for the first step of a block is made at the last kick of the previous block.
- Only for the first step of a run (value unknown): use the initial state at `t_0`, the moon at `t_0` (sync row 0), and `dt = h`.
- **Arc (D1; A0 amendment 2026-11-07).** With the co-moving arc on, a particle can wrap after its level was chosen and before the step that uses it (the GPU wrap sites are before each kick, `stepper.rs` line 474). After a wrap the moon distance changes completely. So compute `L_j` for the particle and for its two periodic images (position and velocity turned about z by -Δθ and +Δθ, as in `ArcGeometry::wrap`), and take the largest. Without the arc only the particle itself is used, so runs without the arc are not changed by this item.
- **Collisions (K2, K3; A0 amendment 2026-11-07).** A collision at a step boundary changes the velocity after the level was chosen. The level is not chosen again. The velocity change is of the order of the local velocity dispersion (mm/s to cm/s), which is small compared with `v_eff` near a moon: `v_eff >= sqrt(2 GM_j / d_eff)` = 0.021 km/s at 50 km from Prometheus.
- **Block-length dependence.** The levels are a function of the particle state at the kicks, not of the block. Different block lengths change the particle only by rounding (merged and split drifts differ at about 1e-16 relative, as today), so a borderline `d_eff` can give a different L for a few steps. The result is then statistically the same, not bit for bit. This is acceptable because chaotic orbits are compared by statistics only (PLAN 10) and CPU and GPU already differ by precision. The test "block lengths 4096, 1000 and 37" (section 6) checks that the particles agree to the level of the step error. With L = 0 everywhere the result is bit for bit that of today for any block length.
- No hysteresis. A level that depends on the state at the start of the step breaks time-reversal symmetry; the energy test D (section 6) measures what that costs.
- The test per particle per step is one comparison per moon in the common case (`L = 0`), written as `h² v_eff² <= acc² d_eff²` with no logarithm. The 2^L loop runs only when it fails.

**The moon at the sub-kicks.** The table must hold more than today (the observable contract; A3 decides the layout):
1. Velocities `mdot_j` (km/s, 3 values per moon) at the same rows as the positions: the `n` kick rows and the 2 sync rows (block start `t_0` and block end `t_n`) that ICR-006 added. The host takes them from the same ephemeris interpolation (f64).
2. A sub-kick at time `t` uses the **cubic Hermite** polynomial between the two nearest points of the sequence S0 (`t_0`), K_0 (`t_0 + h/2`), K_1, ..., K_{n-1}, S1 (`t_n`): the point before `t` and the point after it. Position error: `Delta^4 |x''''| / 384` with `Delta = h` and `|x''''| = n0^4 a`: `(1.1756e-4 x 356.25)^4 x 139,380 / 384 = 3.1e-6 x 139,380 / 384 = 1.1e-3 km`. Linear interpolation would give the 31.6 km sagitta, and quadratic about 1 km. Both are too big at 40 km.
3. For `n_k = 1` the kick uses the table row itself (no Hermite), so L = 0 is bit for bit today's.
4. The indirect term at a sub-kick is computed from the interpolated moon positions with the existing `indirect_acceleration` formula, on both backends (a twin function). It is not interpolated.

**Scope.** Modes D and D+ only on the GPU (mode C: `Config` error). Chaos and sub-stepping may be combined (A3-ANALYSIS needs it): the shadow particle uses the level of its main particle, so the separation is not a step artefact. The radius rule with the arc stays a `Config` error on the GPU (ICR-006) and on the CPU for now. Sub-stepping is not meant for the web moonlet scenario (W2-MOONLET), where many particles sit inside the trigger distance and a 32-thread group would run at its highest level.

## Why

1. A particle that passes deep inside a moon gets an unbound kick (ICR-006: d <= 0.75 km for Prometheus at h = 356 s). `CpuBackend::step` and `GpuBackend::step` then return `Error::Backend` and `fring-run` stops (`apps/fring-run/src/lib.rs:487`, `during(backend.step(..))`). The inner part of the band cannot finish a map: 72 % of the particles in 139,700 to 139,750 km come within 1 R_H in 10 years (`data/closest_rbins.csv`).
2. The CPU reference has no radius rule, so GPU and CPU cannot be compared when a rule is on. The Rust twin of the rule lives in `fring-gpu`, which `fring-model` cannot depend on.
3. A2-ANALYSIS and A5-ANALYSIS (a) show that the map statistics do not depend on the step: with h/4 the chaotic fraction changes by at most 0.6 sd and the median lambda by at most 1.3 sigma in all six tested windows. But a single pass at less than about 2 R_H is not resolved by h (`h u / d` is 0.17 at 1 R_H for u = 0.03 km/s), and PLAN 7.3 asks for per-particle sub-stepping if that matters. The ICR sets the rule and the interface so that the cost is small and the answer can be checked against IAS15.

### The trigger and its cost (measured)

A2-ANALYSIS gives the worst-case criterion `h v_rel / b < 0.1` with `v_rel` 0.070 km/s (circular, b_crit = 249 km = 4.1 R_H) and 0.109 km/s (eccentric, b_crit = 388 km = 6.3 R_H). The real relative speed at a given distance is smaller, so a rule that uses the actual `u` of each particle triggers much less than a fixed radius. The share of particle-steps in the trigger was measured on the CPU (`runs/logs/e1-icr-f.log`; 12,800 particles of the full band 139,700 to 141,100 km for 2 years, and 6,400 particles each of the eccentric band (e = 0.00235, apse 353.78 deg) at 140,150 to 140,225 km and 140,625 to 140,700 km; the state every 100 steps; 22.7 million and 11.3 million particle-samples; the state at `t_k` stands in for the last kick):

| Option | Band | Inner ecc. | Outer ecc. |
|---|---|---|---|
| A: fixed n = 8 inside 6.3 R_H: share f | 1.13e-4 | 1.84e-4 | 1.24e-4 |
| A: P_group (32 consecutive ids) | 0.0036 | 0.0058 | 0.0039 |
| A: CPU cost 1 + 7 f / GPU cost 1 + 7 P_group | +0.08 % / +2.5 % | +0.13 % / +4.1 % | +0.09 % / +2.8 % |
| A': fixed n = 8 inside 4.1 R_H: GPU cost | +0.9 % | +1.3 % | +0.5 % |
| **B: level rule (this ICR): share with L > 0** | **6.4e-6** | **0** (of 11.3 million) | **4.4e-6** |
| B: CPU cost (mean 2^L) | +0.001 % | +0.000 % | +0.000 % |
| B: GPU cost (mean 2^Lmax over 32 ids) | +0.027 % | +0.000 % | +0.014 % |

- **Real particle order (correction E).** The GPU state buffer is in id order, and the K5-BIN sort (`bin.rs`) only makes an index `sorted[p]` of ids: it does not move the state. The Philox generator draws each particle's a and longitude from its id (`initial.rs: counter(id, draw)`), so ids are in random order in the band. The measured P_group for 32 consecutive ids (0.0036) equals the binomial value for independent particles `1 - (1 - f)^32` (0.0036), as it should.
- An earlier estimate in the plan round (f about 1e-3, GPU +22 %) was too high. It assumed all particles are in radial reach of a moon. Only 25 % of the band is, and a pass inside 6.3 R_H takes about 20 steps.
- The counts behind the rule rows are small: 144 triggered samples (band), 0 (inner ecc., so f < 2.6e-7 at 95 %) and 50 (outer ecc.), so f has an error of about 10 %. The conclusion (cost below 0.1 %) does not depend on it.
- Cost of the test itself (not in the table): one multiplication and one comparison per moon per particle per step, on top of the distances that the kick already computes. This is estimated at a few per cent of a step and is measured in B2.
- Option C (fixed n = 16 inside 1 R_H) has f = 1.2e-6, but it leaves the region 1 to 6 R_H unresolved. Not used.

## Tests and numbers (section 6)

All numbers marked "proposed" are the proposal of this ICR. The E1-REF limits and `accuracy`, `max_level` are decided by AJ (below). `#[ignore]` tests run natively with `--ignored`.

**Twins (`fring-model`, run in the normal `cargo test`):**
- T1 `segment_min_d2`: the cases of `wh::radius_tests` (crossing at 20 km, end point is the minimum, zero length) for `f64`; `f32` agrees with the Wf32 twin; relative error < 1e-6.
- T2 `drift_hits_moon`: passes at radius + 1 km and radius - 1 km (hit / no hit), 43.09 km and 40.63 km.

**D. Energy test (correction D).** Restricted problem: Saturn point mass, Prometheus on a circular orbit (`MoonEphemeris` from `circular.rs`), massless particles, the Jacobi constant `C_J = 1/2 |v_rot|² - 1/2 n_m² (x² + y²) - GM_S/r1 - GM_m/r2` per unit mass in the frame rotating at the moon's rate. Three integrators: sub-stepped WH, today's WH (`[substep]` absent) and IAS15 with epsilon 1e-9 as reference (or WH with h/64).
- (i) One encounter per particle: 2,000 particles, start 10 R_H upstream, impact parameter in 500 each of [0.68, 1), [1, 2), [2, 4.1), [4.1, 6.3] R_H; measure `|Delta C_J|` after the pass.
- (ii) Many encounters: 100 particles with a = 139,380 + 300 to 600 km for 20 years (about 100 encounters each); `|Delta C_J|(t)` against the number of encounters N.
- **Limits (AJ decision 2026-11-08: option a):**
  1. per encounter, b >= 1 R_H: 95th percentile of `|Delta C_J|` <= 1e-6 km² s⁻² (= 3.7e-9 v_c², with v_c² = 272 km² s⁻² at 140,000 km), and <= 0.1 times the value of today's WH for the same particles;

  - Working (estimate): the energy error of a second-order step for one pass is about `(GM_m / d) (h u / d)²`. At d = 200 km: `0.01071 / 200 = 5.4e-5 km² s⁻²`; with `h u / d` = 0.1 at the worst, 0.05 on average, this gives 5e-7 down to 1.4e-7 km² s⁻² per encounter; times sqrt(100) = 1.4e-6 km² s⁻², which is 5e-9 v_c². Today's step has `h u / d` of 0.5 to 1 at d = 63 km, so its error is about 100 times larger. The limits keep a factor of 2 to 5 above this estimate. Reasons:

- **C5.** Particles with close encounters are chaotic. A2 measured: a change of 1e-12 km in one start coordinate gives 4.3e-5 km after 100 days, and a block of 37 steps has 650 block ends. So the maximum measures the chaos, not the code (`AGENTS.md`: compare statistics, never trajectories). The median particle has no strong encounter in 100 days and shows the code: a mistake at the block ends would move every particle, not one. The level agreement (≥ 99.9 % of steps; measured 1.000000) stays.
- **T3.** The error of a cubic Hermite between nodes Δ apart is x'''' s²(1 − s)² Δ⁴ / 24. Its time derivative has its largest value 0.192 Δ³ x'''' / 24 = Δ³ x'''' / 125 at s = 0.211. With Δ = h = 356.25 s and x'''' = n₀⁴ a = (1.1756e-4)⁴ × 139,380 = 2.66e-11 km s⁻⁴: 4.52e7 × 2.66e-11 / 125 = **9.6e-6 km/s**, as measured. A limit of 1e-6 km/s needs nodes 2.1 times closer. The velocity enters only the level rule, through u = |w − ṁ|: at u = 0.03 km/s the relative error is 3e-4. With part 1, sub-stepping is off in production.
- **D relative.** With part 1, this ratio is the evidence for the decision, not a pass condition. It also cannot pass where L = 0 (the ratio is exactly 1).
- **D absolute.** Today's WH is now the production setting, so the absolute limit applies to it.
- **D reference.** The check is there so that the reference error cannot change a pass or a fail. The scale of a pass or a fail is the limit. The measured value can be at the rounding floor itself ([4.1, 6.3): the reference is at 1.1e-13, 1.5e-3 of the sub-stepped value; (ii): 0.02 to 0.42).
- **D conserved quantity.** The backend adds Saturn's reflex acceleration (ADR 0004), a uniform force that is static in the frame rotating with the moon. Its potential g (r · m̂) is part of the conserved quantity. Amplitude: g a = GM_m / a_m = 0.01071 / 139,380 = 7.7e-8 km² s⁻².
