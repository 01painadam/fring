# ICR-002: accelerations in the moon ephemeris (quintic Hermite)
Requested by: A2  Date: 2026-11-01
Status: Accepted

## What

- `fring_model::MoonTrack` gets a required field `accelerations_km_s2: Vec<Vec3<f64>>`, the inertial (Saturn-centred) acceleration of the moon at each sample, in km s⁻². It has the same length as `samples`.
- `MoonEphemeris::validate` checks the length and that every value is finite.
- Backends interpolate with a quintic Hermite polynomial (position, velocity and acceleration at both ends of an interval). There is no cubic fallback.
- Default table interval: 1800 s.
- Interpolation functions live in `fring_model::physics` (`hermite5`, `interpolate_moons`, `interpolate_moons_into`).

## Why

A cubic Hermite polynomial needs an interval of 300 s to reach 10⁻³ km at mid-interval (error r (n Δt)⁴ / 384, with r = 1.4 × 10⁵ km and n = 1.19 × 10⁻⁴ rad s⁻¹). A 30-year table for two moons is then 303 MB. A quintic polynomial (error r (n Δt)⁶ / 46080) needs 1800 s, and the table is 76 MB. Making the field required gives one code path, which is simpler for the GPU.

## Roles affected

- A0: `system.rs` (done by A2 for this ICR, with the tests that build a `MoonTrack`).
- A3: reads three vectors per node and interpolates a quintic in WGSL. In f32 the node-relative form is needed (position resolution in f32 is 0.016 km at 1.4 × 10⁵ km).
- A5: `fring-run` builds the ephemeris with `fring_model::physics::build_ephemeris`.
- A7: the web toy may call the same function in wasm.

## Migration

Every `MoonTrack { .. }` literal gets `accelerations_km_s2`. There is no stored ephemeris file format yet, so no old data exists.

## A0 decision

2026-11-01: Accepted, to keep the 30-year table at about 76 MB instead of 303 MB.
